# 確定成果の節目のお礼と、人間味のある雑談

2026-11-11（JST）。ユーザー指定: 楽天アフィリエイト全体でキャンセル等を除いた確定成果の累計件数を数えます。購入者の人数、商品点数、売上金額、未確定の成果発生件数とは区別します。

## 節目と入れ替え

対象は1・10・50・100・300・500・1,000・10,000件。報告時に複数の節目を超えていても最新のものだけを扱います。初めて累計12件を登録した場合は10件のお礼を用意し、1件のお礼は後から挟みません。「12人購入」などと人数に言い換えません。実数より小さい節目でも自然なように「到達」「節目を迎えた」という表現を使います。

次に実行可能な雑談枠（10:30・12:00・16:00のいずれか）をお礼に置き換えます。投稿枠は増やさず、商品5・雑談3、各SNSで計8回/日のままです。商品枠、未来の枠、20分を超えて遅れた枠はお礼に使いません。

登録が枠の処理開始後だった場合は、その次の雑談枠で扱います。ThreadsとInstagramで各節目を1回ずつ記録します。片方だけ準備に失敗した場合は、そのSNSの次の雑談枠で扱います。新しい節目が報告されれば未送信の古いお礼は差し替えます。

文章は8種類を用意しました。感謝、嬉しさ、迷い、諦めなくてよかったという気持ち、今後も続けたい気持ちなどを使い分けます。ユーザーが希望した気持ちの表現を作者の声として採用し、何か月努力した・毎晩泣いた・家族に支えられた等、未確認の経歴や具体的な苦労話は作りません。商品のPRやアフィリエイトURLは入れません。

全文は`npm run milestone:examples`、またはActionsの **Rakuten confirmed milestones (no posting)** の`operation: examples`で確認できます。これは文章例の表示だけで、実際に成果が発生したという登録はしません。AI課金も投稿もありません。

## 当面は手動で件数を確認

楽天の成果レポートを自動取得する連携は未実装です。定期処理が購入者を特定したり、SNSから注文を推測したりすることはありません。

初回の準備:

1. Supabase SQL Editorで、001・002適用済みの同じプロジェクトに[003_milestone_state.sql](../supabase/migrations/003_milestone_state.sql)の全文を貼り付け、Run。
2. 既存テーブルやデータは削除せず、設定データを安全に更新するための専用RPCだけを追加します。既存の予定枠や料金設定は変更しません。
3. Actionsの **Rakuten confirmed milestones (no posting)** を`operation: status`で実行し、`milestoneVersion: 1`を確認します。初期状態の`state: null`は正常です。架空の成果を登録せずに準備を確認できます。

件数が確認できたとき:

1. 楽天アフィリエイトの成果レポートで、全体の確定成果の累計件数を自分で確認します。月間件数だけを累計として入れないでください。
2. Actions → **Rakuten confirmed milestones (no posting)** → Run workflow。Branchは`main`。
3. `operation: record`を選び、`confirmed_count`に累計件数を半角数字・カンマなしで入力します。
4. `report_confirmed`は、そのレポートを確認できた場合だけチェックして実行します。見本の件数や架空の件数を実DBへ登録しないでください。
5. `operation: status`で累計と各SNSの状態を確認できます。

購入者名、メールアドレス、注文番号、商品明細は入力しません。同じ累計を再登録しても投稿済みの節目は復活しません。件数を訂正して減らすと、未送信で到達していない節目は停止します。すでに投稿したお礼を削除したり再投稿したりはしません。より低い節目を後から埋め直すこともありません。

## 重複と送信結果不明への対応

節目の状態は既存のsettingsに保存し、リビジョンによるcompare-and-swapを使って別ランナーの更新を上書きしないようにします。設定データは既存の暗号化バックアップ・エクスポート／復元に含まれます。

送信前に件数が変わり、選ぶべき節目も変わっていたら送信を停止します。公開済みなら媒体別に完了として記録します。通信切断等で送信結果が不明なら保留し、次の枠で同じお礼を自動再送しません。実際のメディアIDを確認した照合でのみ完了へ移します。

DRY_RUNのリハーサル履歴は本番の履歴と別に保存します。テストで使った節目が本番で消えることはありません。現在の定期実行はDRY_RUNなので、お礼を実際に公開することはありません。

Instagramのお礼には本文と一致した自作画像が必要です。DRY_RUNではローカルの文字画像と架空URLだけを使い、これを本番Metaアダプターへ渡すと拒否します。本番の画像配信基盤と投稿ランナーは引き続き残件です。画像が用意できないときに、通常の雑談画像へお礼文だけを付けて公開することはありません。

## 通常の雑談の文体

少し迷う本音、道具選びへのこだわり、小さなツッコミを増やしました。1文目の後だけ改行し、残りは1段落。6種類を回し、問いかけは連続3投稿で最大1回。毎回教訓やきれいな結論で締めません。

例:

> おしゃれな部屋にしたいけど、リモコンは近くにいてほしい。
> ひざ掛けも、本も、使う物まで遠くにしまうとちょっと困る。写真みたいなすっきり感に憧れつつ、くつろぐための物も残したい。都合のいい願いだけど、どっちも本音。

> 便利なのはわかるけど、その色だけちょっと惜しい。
> キッチン道具を選ぶとき、最後に引っかかるのがそこだったりする。機能の話をしてるのに、頭の中では棚との色合わせ。毎日目に入る物だし、見た目にも一票入れたい。

人間味を出すために、本人の購入・使用経験、家族構成、昨日の出来事などを作ることはしません。OpenAIへ渡す指示にもこの方針を追加しています。
