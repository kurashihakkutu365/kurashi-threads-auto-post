## 本番を止める必須条件

* 本番キー・各SNSの公開/返信権限・必要なApp Reviewが未確認。
* 許諾済みの実商品画像2枚・画像公開配信条件・一覧サイト掲載条件が未登録。
* 楽天の現行仕様を取得できず、実商品検索はモックのみ。楽天APIの画像URLを許可として扱わない。
* Actionsのディスクはジョブごとに消える。SQLiteやActions artifactsだけで無人本番の永続DBとみなさない。
  Supabaseの予約・一意制約・投稿状態は**サーバー側トランザクション**で実装した。
  利用者のプロジェクトで[接続確認](SUPABASE_SETUP.md)に成功し、`STORAGE_BACKEND=supabase`を設定する必要がある。
  返信キューのリモートRPC接続は未完了。RESTで読んでから別リクエストで書く方式は競合制御にならない。
* 実画像の期限切れURLを検出するHEAD/GET確認、公開ホストの厳密allowlistとDNS/リダイレクト対策が未接続。
  `publicHttps`は文字列の補助検証で、DNS rebinding対策を保証しない。
* コンテナ状態を見ただけでは公開メディアIDを特定できない。照合不能はunknownで保持し、自動再公開しない。
* 無料Webhook基盤と遅延キューは未デプロイ。返信時刻は保証しない。5分おきのActions常時起動は実装しない。

## 回復手順

1. 全停止フラグを有効にし、共有DBのバックアップとチェックサムを確保する。
2. 別DBへ復元し、整合性・schema version・行数・投稿番号・許諾・unknown状態を確認する。
3. `sending`/`unknown`は再送しない。公式APIからメディアIDを一意に照合できた場合だけpublishedへ移す。
4. DB接続・画像期限・認証・規約・料金を再確認し、DRY_RUNで期限内の新しい枠を検証する。
5. 本番移行条件を満たしてから本番ランナーの実装・有効化を別途行う。

## 保守目安

月1回、モデル/API料金・無料枠・規約・トークン・画像許諾期限・失敗/費用レポートを確認。
月次の暗号化バックアップと隔離環境での復元試験、期限切れ画像の配信撤去を運用に追加する。
Node 24のサポート期間内に次のサポート対象LTSへ更新する。5年間の無保守運用は保証しない。

ログは90日で整理するが、商品番号・投稿/返信の重複防止記録・画像許諾証跡は保持する。
個人情報を含むイベント本文は除外時に保存せず、完了後の保持期限経過で本文/著者を消す。
バックアップとエクスポートには許諾証跡や返信データが含まれるため、平文を公開ページやartifactへ置かない。
新しいバックアップworkflowはAES-256-GCM暗号文だけを保存し、鍵はGitHub Secretsと別の安全な復旧保管先で管理する。
